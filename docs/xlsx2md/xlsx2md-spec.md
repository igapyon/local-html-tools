# xlsx2md 仕様

## 1. 文書概要

`xlsx2md` は、Excel 形式の設計書ファイル (`.xlsx`) を解析し、シート単位の Markdown 文書へ変換するツールである。

本ツールの目的は Excel の見た目を再現することではなく、設計書としての構造・意味・追跡可能性を保ちながら、生成 AI が入力として処理しやすい Markdown に変換することである。

本ツールは、単なる `Excel -> Markdown` ではなく、`設計書構造抽出 -> Markdown` として設計する。

## 2. 適用範囲

### 2.1 対応入力形式

- `.xlsx`

### 2.2 非対応入力形式

初版では以下を対象外とする。

- `.xls`
- `.csv`

### 2.3 想定対象文書

本ツールは、以下のような設計書系 Excel を主対象とする。

- プログラム設計書
- 画面設計書
- バッチ設計書
- IF 設計書
- 項目定義書
- テーブル定義書
- テストケース定義書

## 3. 基本設計方針

### 3.1 出力目的

出力 Markdown は、以下を満たすことを目的とする。

- 生成 AI が入力として解釈しやすい
- 人間が読んで意味をある程度把握できる
- トレーサビリティを確保できる
- 元の Workbook / Sheet / Range / Anchor を追跡できる

### 3.2 出力方針

- 出力はシート単位とする
- 各シートは 1 つの Markdown ファイルとする
- Workbook 名は必須メタ情報として保持する
- 表検出は罫線を主要手掛かりとし、空白関係・密度・ヘッダ性を補助手掛かりとする
- 見た目の忠実再現ではなく、構造と意味の保存を優先する
- Markdown 本文の既定値は Excel 表示寄りとする
- Excel 表示寄りとは、人間が既存の設計書 Excel 上で見ている値を生成 AI と共有しやすい形を優先することを意味する
- ただしピクセル単位の見た目再現は目的とせず、表示値・構造・トレーサビリティの両立を優先する

### 3.3 実装方針

- 配布形態は Single-file Web App とする
- 画面 UI は `lht-cmn/` を正本とし、原則 `lht-*` コンポーネントを利用する
- 実装の正本ソースは TypeScript とする
- 自動テストを前提とし、主要な変換ロジックには継続的にテストを追加する

## 4. 出力単位およびファイル構成

### 4.1 出力単位

- 1 Workbook を入力とする
- 1 Sheet ごとに 1 Markdown ファイルを出力する

### 4.2 出力ファイル例

入力:

- `sales.xlsx`

出力:

- `sales_001_Summary.md`
- `sales_002_Detail.md`

`raw` / `both` モード時の出力例:

- `sales_001_Summary_raw.md`
- `sales_001_Summary_both.md`

### 4.3 出力ディレクトリ構成

出力ディレクトリは以下の構成を基本とする。

```text
output/
  sales_001_Summary.md
  sales_002_Detail.md
  assets/
    Summary/
      image_001.png
      image_002.png
    Detail/
      image_001.png
```

### 4.4 ファイル命名

- Markdown ファイル名には Workbook 名、シート順、シート名を利用する
- シート順は Workbook 内の物理順序に従う
- シート名にファイル名として不適切な文字が含まれる場合はサニタイズする
- サニタイズ時は、ファイルシステム上で不安定な記号、空白、連続区切りを整理して保存名へ反映してよい
- 例: シート名 `A B-東京&大阪.01` は、保存名で `A_B-東京_大阪.01` のように変換してよい
- 出力モードが `display` 以外の場合、Markdown 保存名には `_raw` または `_both` のサフィックスを付与してよい
- 全シート連結保存や ZIP 保存でも、`display` 以外のモードでは同様にモード名サフィックスを付与してよい

## 5. Markdown 出力構造

### 5.1 基本構造

各 Markdown は、以下の構造を基本とする。

```markdown
# Summary

## ソース情報
- Workbook: sales.xlsx
- Sheet: Summary

## 本文

このシステムは XXX です。
YYY システムとの連携を ZZZ です。

### 表001 (C3-F5)

| Region | Sales | Target | Status |
| --- | --- | --- | --- |
| East | 120 | 100 | Good |
| West | 90 | 100 | Below |

### 画像001 (C7)
- File: assets/Summary/image_001.png

![image_001](assets/Summary/image_001.png)
```

### 5.2 出力要素

各 Markdown には以下を含める。

- シート名
- ソース情報
  - Workbook 名
  - Sheet 名
- 地の文
- 必要に応じて表
- 必要に応じて画像情報

### 5.3 ソース情報

トレーサビリティ確保のため、各 Markdown 冒頭に以下を必ず出力する。

- Workbook 名
- Sheet 名

Workbook 名は省略しない。

### 5.4 内部 ID の扱い

内部的な表 ID や画像 ID を保持してよいが、本文の主見出しでは必須としない。必要な場合のみ補助メタ情報として扱う。

## 6. 地の文抽出仕様

### 6.1 基本方針

- 表候補に含まれなかった非空セルを地の文候補として扱う
- 地の文候補は、近接したセル群を段落ブロックとしてまとめる
- 1 セルごとに独立した文章としては扱わず、行方向・列方向の近接性を考慮して連結する

### 6.2 地の文ブロック化ルール

- 同一行で隣接する文字セルは半角スペース区切りで連結する
- 連続する行が近い開始位置から始まる場合は同一段落候補として扱う
- 1 行以上の明確な空白行がある場合は段落を分割する
- 罫線で囲まれた領域は地の文ではなく表候補を優先する
- 表候補外の非空セル群は、上から下、左から右の順で Markdown へ出力する

### 6.3 初版の扱い

- 初版では「見出し」「注記」「本文」を細かく分類しすぎず、まずは地の文ブロックとして出力する
- 将来必要であれば、見出し候補や注記候補の分類ルールを追加する

## 7. 表検出仕様

### 7.1 基本方針

表検出は全自動で行う。ただし検出結果は絶対確定ではなく、設計書として妥当な表範囲を推定するものとする。

### 7.2 主要手掛かり

表検出の主要手掛かりとして、以下を採用する。

- 罫線
- 前後の空白関係

### 7.3 罫線の役割

罫線は、表の存在検出および境界推定に使用する。

利用対象とする罫線情報:

- top
- bottom
- left
- right

考慮する観点:

- 外枠が存在する
- 内部グリッドが存在する
- 矩形としてまとまりがある
- 2 行 x 2 列以上の領域を形成する

外枠がなくても、規則性を持って線が引かれている場合は表候補として扱ってよい。

### 7.4 表検出手順

表検出は以下の順で行う。

1. シート内セルの罫線情報を取得する
2. 罫線により形成される矩形領域を表候補として抽出する
3. 連続する空白がなく、塊となっていることを確認する
4. スコアリングにより表候補を評価する

### 7.5 補助判定

必要に応じて、以下を補助情報として用いてよい。

- 非空セル密度
- 先頭行のヘッダらしさ
- 列型の一貫性

## 8. 表候補のスコアリング

### 8.1 基本方針

- 表検出は二値判定ではなく、表候補ごとのスコアリングで扱う
- 主要手掛かりは罫線としつつ、密度・ヘッダ性・列型一貫性を補助情報として用いる
- 一定スコア以上の領域を表として採用し、それ以外は地の文候補へ回す

### 8.2 加点要素

- 外枠の罫線がある
- 内部グリッドの規則性がある
- 2 行 x 2 列以上の矩形を成す
- 非空セル密度が高い
- 先頭行がヘッダらしい短い文字列で構成される
- 列ごとの値の型や粒度に一貫性がある

### 8.3 減点要素

- 結合セルが過剰に多く、通常の表構造を崩している
- 長文セルばかりで段落ブロックに近い
- 罫線が弱く、単なる縦方向の文章列に見える

### 8.4 判定の目安

- 高スコア領域は表として採用する
- 中スコア領域は弱い表候補として扱い、将来は警告や補助表示の対象にできる
- 低スコア領域は地の文候補として扱う

### 8.5 初版の実装方針

- 初版では単純な重み付き加点方式を採用する
- 学習ベースや複雑な統計推定は行わない
- 判定理由を内部ログやデバッグ情報として保持できる設計が望ましい

## 9. 表の役割推定

### 9.1 推定結果の利用

推定した役割は、Markdown セクション見出しや内部メタ情報に反映してよい。

### 9.2 初版の扱い

初版では複雑な役割分類は必須とせず、`表001` のような連番見出しを基本とする。将来、見出し語や周辺セルから役割名を推定できるようにしてよい。

## 10. セル値処理仕様

### 10.1 通常セル

通常セルは、その値を文字列化して出力する。

### 10.2 数式セル

数式セルは可能な限り解決する。

解決対象:

- `=A1`
- `=Sheet2!B3`
- `='画面項目一覧'!C10`

非対応:

- 外部 Workbook 参照
- `='[master.xlsx]一覧'!A1`

### 10.3 数式セルの出力値決定順

数式セルの出力値は、以下の優先順で決定する。

1. cached value
2. 式文字列
3. 解決状態メタ情報保持

### 10.4 cached value

Excel に保存済みの計算結果が存在する場合は、それを採用する。

### 10.5 フォールバック

保存済み計算結果が存在しない場合は、式文字列をそのまま出力値として採用する。空欄にはしない。

### 10.6 外部参照

外部参照は非対応とする。解決は行わず、式文字列を保持する。

### 10.7 解決状態メタ情報

数式セルについては、以下の状態を内部メタ情報として保持する。

- `resolved`
- `fallback_formula`
- `unsupported_external`

## 11. 未計算 Workbook の扱い

Excel が未計算状態で保存されている場合、数式セルに対する cached value が存在しない場合がある。

この場合、本ツールは以下の動作を行う。

- 式文字列にフォールバックする
- 情報を欠落させない
- 解決状態として `fallback_formula` を保持する

未計算 Workbook はエラーとはみなさない。

## 12. 文字列化方針

### 12.1 基本方針

Markdown 出力においては、最終的なセル値は文字列として扱う。

### 12.2 数値・日付・論理値

以下は原則として表示値相当を文字列として出力する。

- 数値
- 日付
- 真偽値

厳密な型保持は Markdown 側では要求しない。必要な内部型保持は実装側で行ってよい。

### 12.3 参照解決後の扱い

参照解決された値も、Markdown 出力時には単なる文字列値として出力する。

### 12.4 表示値優先の考え方

- `xlsx2md` の既定出力は、Excel の表示値に近い文字列を優先する
- これは既存の設計書 Excel を人間と生成 AI が共通参照する前提に合わせるためである
- 設計書レビューや問い合わせでは、Excel 上で見えている値と Markdown 上の値が近いことを重視する
- したがって、初版標準モードは `AI 向け抽象化` よりも `人間と AI の共通理解` を優先する

### 12.5 内部保持と将来モード

- 表示値を Markdown に出力する場合でも、内部的には `raw_value` を保持する
- 可能であれば `numFmtId` と `formatCode` も保持する
- 数式セルについても、cached value または再解決結果が得られた場合は、可能な範囲でセル書式を再適用し、`display` では表示値寄りに出力する
- 例: `=DATE(2024,3,17)` が日付書式セルに置かれている場合、`display` では `2024/3/17`、`raw` では `45368` として扱ってよい
- 将来的には以下の出力モードを選択可能としてよい
- `display`: Excel 表示値を優先する既定モード
- `raw`: 元の内部値を優先するモード
- `both`: 表示値を本文に出しつつ、必要に応じて raw 値を補助表示するモード
- `both` の補助表示は、たとえば `2024/1/1 [raw=45292]` のような簡潔な表記としてよい
- 初版では `display` を標準とし、`raw` および `both` は拡張余地として位置づける

### 12.6 出力モードの具体例

```markdown
date
display: 2024/1/1
raw: 45292
both: 2024/1/1 [raw=45292]

currency
display: ¥1,024,768
raw: 1024768
both: ¥1,024,768 [raw=1024768]

fraction
display: 3/4
raw: 0.75
both: 3/4 [raw=0.75]

formula-date
display: 2024/3/17
raw: 45368
both: 2024/3/17 [raw=45368]
```

## 13. 結合セルの扱い

### 13.1 基本方針

- 結合セルは Markdown テーブル上で完全再現しない
- 結合範囲の左上セルを代表値セルとして扱う
- 結合範囲内の他セルには、空文字ではなく補助トークンを出力する
- 結合範囲そのものは内部メタ情報として保持する

### 13.2 初版の結合セル出力ルール

- 横方向結合で展開されるセルには `[MERGED←]` を出力する
- 縦方向結合で展開されるセルには `[MERGED↑]` を出力する
- 左上の代表セルには元の値を保持する
- 複合結合範囲に含まれるセルも、左上セルへの従属を示す補助トークンとして扱う

### 13.3 補足

- `[MERGED←]` および `[MERGED↑]` は、変換器が補完した構造トークンであり、元のセル値ではない
- 人間可読性を優先する将来モードでは `(同左)` や `(同上)` のような表現を選択可能としてよい

## 14. 画像対応仕様

### 14.1 対応レベル

画像対応は、画像そのものと位置情報を残すことを目的とする。

### 14.2 対応内容

- 埋め込み画像を抽出する
- 画像ファイルとして保存する
- Markdown から相対リンクする
- 画像のアンカー位置を保持する

### 14.3 保持する画像情報

各画像について、以下を保持する。

- シート名
- 画像ファイル名
- 出力先パス
- アンカー位置

### 14.4 画像位置

初版では、画像位置はアンカーセルとして保持する。

例:

- `C3`
- `F12`

### 14.5 Markdown 出力例

```markdown
## 画像

### Image 1 (F2)
- File: assets/Summary/image_001.png

![image_001](assets/Summary/image_001.png)
```

### 14.6 非対応範囲

初版では以下は行わない。

- OCR
- 画像内容の意味理解
- 画像要約
- 図表分類
- ピクセル単位レイアウト再現

## 15. トレーサビリティ要件

### 15.1 基本方針

変換後 Markdown から、元の Excel 上の出典を追跡可能でなければならない。

### 15.2 必須保持情報

以下を必須で保持する。

- Workbook 名
- Sheet 名
- 表の Range
- 画像の Anchor
- 画像ファイルパス

### 15.3 追跡単位

- 文書単位: Workbook
- ファイル単位: Sheet
- セクション単位: 表または画像
- 領域単位: Range または Anchor

### 15.4 Workbook 名の扱い

Workbook 名はトレーサビリティ上必須のため、各 Markdown に必ず出力する。

## 16. 想定 UI

初版の UI は以下を基本とする。

1. `.xlsx` ファイル選択
2. シート一覧表示
3. 対象シート選択
4. 変換オプション指定
5. Markdown プレビュー
6. コピーまたは保存

### 16.1 初版の主要オプション

- 対象シート: 単一 / 全シート
- 先頭行をヘッダーとして扱う
- 空行を除外する
- 空列を除外する
- シート名を Markdown 見出しとして出力する
- セル内改行を `<br>` にする
- 余分な前後空白を trim する

### 16.2 UI 実装方針

- 画面実装では `lht-cmn/README.md` の方針に従う
- `md-*` を画面側で直接多用せず、原則 `lht-*` を利用する
- 単一 HTML 配布を維持しつつ、開発時は `*-src.html` と分割ソースで保守する

## 18. 技術方針

- 単一 HTML で配布する
- 実装は `docs/xlsx2md/` 配下に閉じる
- ビルド方式は既存の `*-src.html` + 単一 HTML 生成パターンを踏襲する
- 可能な限り依存を増やさず、必要なら最小限の同梱を検討する
- ローカルブラウザ内で完結し、サーバ送信を前提にしない
- UI 共通部品は `lht-cmn/` を利用する
- アプリ本体ロジックの正本ソースは `src/xlsx2md/ts/*.ts` とする
- 配布用 JavaScript は TypeScript から生成する
- テストは自動実行可能な形で `docs/xlsx2md/tests/` に配置する

### 18.1 想定ディレクトリ構成

```text
docs/xlsx2md/
├── README.md
├── xlsx2md-spec.md
├── xlsx2md-src.html
├── xlsx2md.html
├── src/
│   └── xlsx2md/

│       │   ├── main.ts

│       └── js/
│           ├── main.js

└── tests/
    └── xlsx2md-main.test.js
```

### 18.2 テスト方針

- 主要な変換ロジックは UI から分離し、単体テスト可能な形にする
- 少なくとも以下を自動テスト対象に含める
- 地の文抽出
- 表候補スコアリング
- 結合セルの `[MERGED←]` / `[MERGED↑]` 展開
- 数式セルのフォールバック処理
- シート単位 Markdown 出力の基本整形

## 19. XML カバー範囲

### 19.1 基本方針

- `xlsx2md` は `.xlsx` 内部 XML のすべてを完全再現することを目的としない
- 初版では、設計書の構造抽出と Markdown 化に必要な中心要素を優先的に扱う
- XML 上の表現差異が存在しても、最終的に「セル値」「構造」「トレーサビリティ」が取れればよい

### 19.2 現在カバー済みの XML 要素・仕組み

- `xl/workbook.xml`
  - Workbook 内のシート一覧
  - シート順序
  - シート名
- `xl/_rels/workbook.xml.rels`
  - Workbook から worksheet への解決
- `xl/worksheets/sheet*.xml`
  - セル座標
  - 行列配置
  - セル値
  - `f` による数式
  - `v` による cached value
  - `inlineStr`
  - `mergeCells`
- `xl/sharedStrings.xml`
  - shared string 参照
- `xl/styles.xml`
  - 罫線情報
  - `numFmtId`
  - `formatCode`
  - 日付系表示値の一部文字列化
- `xl/worksheets/_rels/sheet*.xml.rels`

## 24. 生成 AI 入力としての Markdown 採用理由

本ツールは、出力形式として Markdown を採用する。

理由は以下の通りである。

- 見出し、箇条書き、表といった軽量構造を持つ
- 生成 AI が解釈しやすい
- 人間も読みやすい
- HTML や XML より冗長性が低い
- 設計書の中間表現として扱いやすい

## 25. 最終要約

`xlsx2md` 初版仕様の要点は以下の通りである。

- 入力は `.xlsx` のみ対応
- 出力はシート単位の Markdown
- Workbook 名はトレーサビリティのため必須
- 表検出は罫線を主要手掛かりとし、空白関係とスコアリングを併用する
- 地の文は表候補外の非空セル群から段落ブロックとして抽出する
- 数式は可能な限り解決し、未計算時は式文字列へフォールバックする
- 結合セルは左上代表値 + `[MERGED←]` / `[MERGED↑]` で表現する
- 外部参照は非対応
- 画像は抽出し、アンカー位置つきで保持する
- OCR や画像意味解析は初版対象外
- 出力形式は、生成 AI 入力に適した Markdown とする

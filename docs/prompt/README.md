## 対象ファイル

- 配布物（生成物）:
  - `docs/prompt/prompt-gen.html`
- 編集元:
  - `docs/prompt/prompt-gen-src.html`
  - `docs/prompt/src/prompt-gen/css/app.css`
  - `docs/prompt/src/prompt-gen/ts/prompt-definitions.ts`
  - `docs/prompt/src/prompt-gen/ts/prompt-definitions-ai-expansion.ts`
  - `docs/prompt/src/prompt-gen/ts/prompt-definitions-ai-suggest.ts`
  - `docs/prompt/src/prompt-gen/ts/prompt-definitions-popular.ts`
  - `docs/prompt/src/prompt-gen/ts/main.ts`
- テスト:
  - `docs/prompt/tests/prompt-gen-main.test.js`

`prompt-gen.html` は直接編集せず、編集元を更新してビルドで反映します。
候補ボタンの追加・変更・削除は `docs/prompt/src/prompt-gen/ts/prompt-definitions.ts` を変更対象とし、`prompt-gen.html` や生成済み `js` を直接編集しません。

`docs/prompt/src/prompt-gen/ts/prompt-definitions-ai-expansion.ts` には、既存 `prompt-definitions.ts` の延長上にある新規候補を生成AI視点で展開した `X` 系列を配置します。これらは UI 上では他の候補と同列に検索・表示されますが、定義ファイルは既存系列と分離して管理します。

`docs/prompt/src/prompt-gen/ts/prompt-definitions-ai-suggest.ts` には、既存系列の流れから自然に追加されそうな新規候補を生成AI視点で提案する `S` 系列を配置します。これらも UI 上では他の候補と同列に検索・表示されますが、既存系列や `X` 系列とは分離して管理します。

`docs/prompt/src/prompt-gen/ts/prompt-definitions-popular.ts` には、世間で広く使われている定番プロンプトを整理した `P` 系列を配置します。これらも UI 上では他の候補と同列に検索・表示されますが、自分の実務正本である `A` 系列とは分けて管理します。

### 系列の考え方

- `A` 系列:
  - 既存の基本系列です。人間にとって自然で簡潔な依頼文を中心に構成します。
  - 直近では `A400-A403` として、不具合報告起票の 4 軸
    (`修正担当者向け` / `管理用` / `品質分析用` / `顧客対応用`)
    を正本系列へ追加しました。
- `X` 系列:
  - `A` 系列と目的感を大きく変えずに、生成AIが誤解しにくいように精密化した系列です。
- `S` 系列:
  - 既存系列の流れから自然に追加されそうな新規候補を、生成AI視点で提案する系列です。
  - 既存 `A` 系列のどこから派生した提案かを示したい場合は、`S101-001` のような枝番形式を用います。
- `P` 系列:
  - 世間で広く使われている、普及度の高い定番プロンプトを整理する系列です。

### P 系列から A 系列へ移すときの運用

- `P` 系列は定番整理の置き場、`A` 系列は自分の実務正本の置き場として扱う
- `P` 系列で試した候補のうち、日常的に使う価値が高く、実務正本にしたいものだけを `A` 系列へ移す
- `A` 系列へ移すときは、単純コピーではなく、実務で使う前提で文面・項目・対話手順を見直す
- `A` 系列は現状 3 桁番号で運用しており、枝番は使わない
- そのため、`P1403-501` のような枝番付き候補を `A` 系列へ移す場合は、内容に近い空き 3 桁帯を新設または利用する
- 今回の不具合報告起票 4 軸は、`P1403-501-P1403-504` から `A400-A403` へ移植した
- `P` 側は定番整理として残し、`A` 側を正本として育てる
- `A` へ移植したあと、関連する `docs/prompt/*.md` にも正本側の位置づけを反映する

### ハルシネーション防止ルールの運用

`prompt-gen` では、事実誤認や「もっともらしい補完」が事故につながりやすい候補について、ハルシネーション防止ルールを明示的に組み込みます。

背景として、生成AIは次の傾向を持ちます。

- 空欄を自然に埋めようとする
- それらしい文面に整えようとして、会話や入力にない事実を補完しやすい
- 報告票、PR本文、引継文、整理文のような「整った出力」を求められるほど、捏造が見えにくくなりやすい

このため、単に Markdown で整えるだけではなく、「何を書いてよいか」「何を書いてはいけないか」を明示する必要があります。

現在は、`docs/prompt/src/prompt-gen/ts/prompt-markdown-util.ts` に次の共通関数を置いて運用しています。

- `getStrictHallucinationPreventionInstruction()`
  - 事実ベースの記録、報告、引継、対外説明のように、誤りコストが高い用途向け
  - 会話や入力にない情報を補完しない
  - 根拠がない内容を確定情報として書かない
  - 情報不足なら追加質問し、だめなら `不明 / 未確認 / 要確認` と明示する
  - 推測は `推測:` と明示し、未確認事項を事実として書かない
- `getSoftHallucinationPreventionInstruction()`
  - レビュー、再確認、資料整理、図解化、複数情報統合のように、一定の推論や再構成は必要だが、事実と推測の混同は避けたい用途向け
  - 事実と推測・評価・提案を区別する
  - 断定しきれない内容は断定しない
  - 不明点は不明のまま扱う

### A 系列への適用方針

`A` 系列は、次の 3 区分で扱います。

- 強い版を入れる
  - 事実誤認がそのまま運用事故や説明事故になるもの
  - 例: 不具合報告、PR文面、Release文面、引継、作業状況整理
- 弱い版を入れる
  - 推論や再構成は必要だが、根拠のない断定は避けたいもの
  - 例: レビュー、再確認、Markdown整理、図解化、転用可否判断
- 不要
  - 形式指示、態度指示、創作寄りのものなど、効果が薄いもの

現時点では、不要と判断したものを除き、`A` 系列の対象候補にはすべて何らかのハルシネーション防止ルールを適用済みです。

### X 系列への適用方針

`X` 系列も、基本的には `A` 系列と同じ考え方で扱います。

- `A` 側で強い版が必要なものに対応する `X` は、原則として強い版を入れる
- `A` 側で弱い版が必要なものに対応する `X` は、原則として弱い版を入れる
- `A` 側で不要なものに対応する `X` も、原則として不要とする

ただし、`X` 系列は AI 向けに詳細化されており、出力構造や記入項目が明確なぶん、空欄補完の圧が高くなることがあります。そのため、`A` より厳しめに扱ってよい候補がある前提で判断します。

現時点では、不要と判断したものを除き、`X` 系列の対象候補にもすべて何らかのハルシネーション防止ルールを適用済みです。

### S 系列への適用方針

`S` 系列も、基本的には `A` 系列や `X` 系列と同じ考え方で扱います。

- 会話内容、ファイル実在性、決定事項、再開情報のように、事実誤認が次の作業に直結するものは強い版を入れる
- 候補列挙、優先順位づけ、論点整理、図解化のように、一定の再構成や提案を含むものは弱い版を入れる
- `S` 系列は「提案系」であっても、実在しないファイル、読んでいない文書、会話にない決定事項をそれらしく補完しやすいため、原則として不要扱いにしない

現時点では、`S` 系列の対象候補にもすべて何らかのハルシネーション防止ルールを適用します。

### P 系列への適用方針

`P` 系列は数が多く、用途差も大きいため、`A` / `X` / `S` よりも「性質ごとの整理」を強めて扱います。

- 事実抽出、報告文面、通知文面、再開支援のように、そのまま運用物になりやすいものは強い版を入れる
- 分析、比較、依存整理、因果整理、図解化のように、再構成や整理は必要だが、事実と推測の混同を避けたいものは弱い版を入れる
- 翻訳、単純リライト、平易化、発散アイデア、憑依系のように、ハルシネーション防止ルールの効果より表現自由度のほうが重要なものは不要扱いにする

`P` 系列は世間的な定番プロンプト集ですが、定番であることと、根拠なく補完してよいことは別です。特に報告・通知・再開系は、定番用途でも誤記や捏造のコストが高いため、個別に強めに扱います。

- 個別候補の分類一覧、分類理由、見直し余地は `docs/prompt/prompt-definitions-popular.md` 側で管理します。
- `P` 系列へ新規候補を追加するときの判定テンプレートも `docs/prompt/prompt-definitions-popular.md` 側で管理します。
- `P` 系列は件数が多いため、まず性質ごとに大枠を決め、必要性が高い候補から段階的に個別適用を進めます。
- `P` 系列で現在も `不要` に残しているものは、未整理ではなく、当面は「自由度優先として確定」とする扱いです。

### 新規候補追加時の共通判定テンプレート

系列を問わず、新しい候補へハルシネーション防止ルールを入れるか判断するときは、まず次を確認します。

- その出力は、そのまま運用物、共有物、記録物になるか
- 会話や入力にない事実を補完すると事故になりやすいか
- 推論や再構成は必要か
- 主目的は整理か、表現変換か、発散か

判定の目安は次のとおりです。

- `強い版`
  - 報告、通知、引継、再開支援、決定事項抽出のように、誤りがそのまま運用事故になりやすい
- `弱い版`
  - 前提整理、依存整理、レビュー、図解化のように、再構成は必要だが事実と推測の分離が必要
- `不要`
  - 翻訳、単純リライト、平易化、発散、態度指定、憑依のように、抑制より自由度を優先したい

迷った場合は、まず `強い` を検討し、強すぎるなら `弱い`、抑制利益が小さい場合のみ `不要` を選びます。

### 実装上の扱い

- Markdown 出力を強制する候補では、原則として次の順に並べる
  - 本文
  - ハルシネーション防止ルール
  - `○最終的な回答は ~~~~ ...`
- Markdown 囲み出力を要求しない候補では、出力形式は変えず、必要に応じて本文末尾へ強い版または弱い版を加える
- 新しい `A` 候補を追加する際は、次を先に判断する
  - 事実誤認のコストは高いか
  - 出力がそのまま運用物になるか
  - 推論を強く抑えるべきか、事実と推測の分離だけでよいか
  - その結果として、強い版 / 弱い版 / 不要 のどれにするか

### 図解化系列の使い分け

- `S603-5xx`:
  - Mermaid を使った図解化を、生成AI視点の派生提案として扱う系列です。
  - `Mermaid timeline`、`Mermaid flowchart`、`Mermaid mindmap` など、構造化テキストから図へ落とし込みやすい表現を提案する用途を想定します。

  - `図解化テキスト化`、`図解化描画指示`、`概念マップ化`、`タイムライン化`、`フローチャート化`、`マインドマップ化` などを含みます。

- 使い分けの目安:
  - AIに「こういう派生もありそう」と提案させたい場合は `S603-5xx`
  - 定番候補として安定運用したい場合は `P1601` 以降

現在の最小テストは次を対象にしています。

- 候補が一意に絞れたときの PR 文面生成

## 実装メモ

- `prompt-definitions.ts` に候補ボタン定義を集約する
- 候補ボタンの文言や本文追加は `prompt-definitions.ts` を編集して反映する
- 各定義は `id / label / keywords / requiresCommitId / buildBody()` を持つ
- `A400-A403` は、不具合報告起票の正本系列であり、`P1403-501-P1403-504` の定番整理版に対応する
- `main.ts` は検索、選択状態、入力欄表示、生成結果更新、共有リンク生成を担当する
- ハンバーガーメニューから `A / X / S / P` 系列の表示有無を切り替えられ、その設定は `localStorage` に保存される
- 検索は空欄で全候補表示、空白区切りで AND、各語の照合先は label / keywords / かな・カナ・ローマ字展開を含む
- 検索欄が空欄の状態で候補ボタンをクリックした場合は、その候補の系列番号から親番号だけを検索欄へ補完する
  - 例: `A321` -> `321`
  - 例: `P1004-003` -> `1004`

### 入力値制約

- `commitId` や `subject` のような可変入力は、そのまま本文へ埋め込まず、サニタイズ後の値をバッククオートで囲って返す
- 入力値は 1024 文字で打ち切り、以降は切り捨てる
- 制御文字、改行、タブなどは半角スペース 1 個へ変換する
- バッククオートはシングルクオートへ変換する
- これらは prompt injection への最低限の緩和策であり、完全な防御ではない
- `commitId` の文字種制限や、`subject` を命令ではなく文字列値として扱う明示文は、現時点では未実装で TODO 管理とする
- これは prompt injection リスクの軽減を目的とした最低限の制約であり、完全な防御ではない

## 検索とキーワード

- 検索ボックスの挙動と `keywords` の設計方針は [prompt-gen 検索とキーワード設計](./prompt-gen-search-and-keywords.md) を参照する
- `prompt-definitions.ts` の更新時は、候補本文だけでなく検索性もあわせて見直す

## 運用方針

- ビルド後の `docs/prompt/prompt-gen.html` は CDN や別ファイルの CSS / JS に依存しない single-file web app を維持する
- 画面側 UI は原則 `lht-*` を利用し、Material Web 直接利用は `lht-cmn` 内部へ寄せる
- この一連のプロンプトでは、作業結果のうち継続利用価値があるものは markdown (`.md`) ファイルに反映する
- 妥当な既存 markdown ファイルがある場合は、それを更新または追記する
- 妥当な既存 markdown ファイルがない場合のみ、新規の markdown ファイルを作成する
- 正本、補助資料、作業メモの役割を見極め、役割に合った markdown へ反映する
- 無意味に markdown ファイルを増やさず、既存文書との整合を優先する
- 変更後は必要に応じて `npm run build:prompt` と関連テストを実行する

# prompt-definitions-popular

`P` 系列は、世間で広く使われている、または普及度の高い定番プロンプトを配置するための系列です。

ここでいう `Popular` は、「自分の実務で正本として定着している」という意味ではありません。  
`A` 系列のように日常業務で実際に使っている基本系列とは区別しつつ、世間的には有用性が高く、広く見られるプロンプトを整理して置くための枠です。

## 役割

`P` 系列は、次のような目的で使います。

- 世間で普及している定番プロンプトを整理する
- 自分の実務ではまだ採用していないが、有用そうな型を保持する
- `A` 系列へ昇格させる前の観察対象として置く
- `S` 系列のような派生提案ではなく、世間的な定番として位置づける

## 系列の考え方

- `A` 系列:
  - 自分の実務で使う基本系列
- `X` 系列:
  - `A` 系列を、生成AIが誤解しにくいように精密化した系列
- `S` 系列:
  - `A` 系列の流れから自然に派生する新規候補を提案する系列
- `P` 系列:
  - 世間で広く使われている定番プロンプトを整理する系列

## 期待する性質

- 普及度や定番性がある
- このリポジトリの利用者にとっても再利用価値がある
- まだ `A` 系列に入っていなくても違和感がない
- 世間的な型として理解しやすい
- 将来的に `A` 系列へ取り込むかどうかを見極めやすい

## 運用イメージ

`P` 系列では、たとえば次のようなものを扱います。

- 世間でよく見かける要約プロンプト
- 比較表、FAQ、議事録、アジェンダ化のような定番変換プロンプト
- 非技術者向け説明や平易化のような普及度の高い説明系プロンプト
- 形式固定出力や一般的な抽出系プロンプト

現在の `P` 系列では、単純な追加ではなく、「人が何をしたいかの流れ」に沿って上位カテゴリを整理します。

- まず事故を防ぐ
- 何が起きているか把握する
- どう伝えるか整える
- どう比べて決めるか考える
- どう進めるか段取る
- どう残して育てるか整える
- 必要なら図や読解へ広げる

一方で、次のようなものは `P` 系列より他系列が適しています。

- 自分の実務で日常的に使う正本:
  - `A` 系列
  - 例えば、不具合報告起票の実務正本は `A400-A403` として管理し、
    世間的な定番整理は `P1403-501-P1403-504` 側に置く
- `A` 系列の AI 向け詳細版:
  - `X` 系列
- `A` 系列から自然に派生した新規候補:
  - `S` 系列

この意味で `P` 系列は、自分の現場の正本ではないが、世間的な普及度と再利用価値を持つプロンプトを管理するための枠です。

## `P1001` の特性

`P1001` は、通常の standalone な popular prompt 群とは少し異なる、特別な番号帯です。ここは `prompt-gen` 画面下部のドロップダウンで後付けされる文言を、独立した `P` 系列としても検索・再利用できるように格納する `出力補助指示` の領域として扱います。

- `P1001-001-P1001-007`
  - `レビュー結果出力` 系
  - 誤解表現、配慮不足、不快感、攻撃性、センシティブ表現、法令遵守、公序良俗の各観点について、ドロップダウンの `レビュー結果出力` 文言そのものを格納する
- `P1001-011-P1001-017`
  - `内部レビュー` 系
  - 上記と同じ観点について、ドロップダウンの `内部レビュー` 文言そのものを格納する
- `P1001-500` 以降
  - 幻想防止や自己判断メモのように、画面下部の出力オプションやその周辺で使う補助指示を独立プロンプトとして置く拡張帯
  - `P1001-502`
    - 自己レビュー
  - `P1001-503`
    - 最小差分で割り切った点と本来志向していた理想形を分けて補足する

このため `P1001` は、「倫理・配慮」というテーマ帯であると同時に、「出力補助指示の保管場所」という役割も持ちます。

## ハルシネーション防止ルール

`P` 系列は定番プロンプト集ですが、すべてを同じ強さで扱うのは不適切です。`P` 系列には、次のように性質が大きく異なる候補が混在しています。

- 事実抽出や状況整理を行う候補
- そのまま報告文面や通知文面になる候補
- 比較、分析、図解化のように再構成を伴う候補
- 翻訳、平易化、リライト、発散、憑依のように、表現自由度が主目的の候補

このため `P` 系列では、`docs/prompt/src/prompt-gen/ts/prompt-markdown-util.ts` の共通ハルシネーション防止ルールを、候補の性質ごとに使い分けます。

- `getStrictHallucinationPreventionInstruction()`
  - 報告、通知、再開支援、決定事項抽出のように、誤りがそのまま運用事故につながりやすい候補向け
- `getSoftHallucinationPreventionInstruction()`
  - 前提整理、依存整理、因果整理、根拠整理、図解化のように、一定の再構成は必要だが、事実と推測の混同を避けたい候補向け
- 不要
  - 翻訳、単純リライト、平易化、発散アイデア、憑依系など、防止ルールの効用より表現自由度のほうが重要な候補

`P` 系列は「世間的に定番だから自由に補完してよい」のではなく、「定番用途の中でも、誤りコストが高いものには明示的な抑制が必要」という前提で運用します。

## 分類判断の補足

### 強い版にした代表理由

- `P1201-004`
  - 会話や文書にない決定事項を補完すると、そのまま誤った合意記録になりやすいため
- `P1204-006`
  - 議事録は決定事項、未決事項、次アクションの取り違えがそのまま運用ミスにつながるため
- `P1403-001`
  - Issue 文面は後続作業の入口になるため、背景や期待対応の捏造コストが高いため
- `P1403-501-P1403-504`
  - 不具合報告起票は、A 系列の `A400-A403` と同様に事実誤認コストが高いため
- `P1005-004`
  - 事象報告は発生日、影響範囲、現状の補完ミスがそのまま説明事故になりやすいため
- `P1002-001-P1002-004`
  - 法令、規約、権利、機密は確認対象そのものの取り違えが危険であり、未確認事項をそれらしく断定させない優先度が高いため
- `P1204-005`
  - メール文面はそのまま送信されやすく、入力にない事実や判断の補完を防ぐ必要があるため
- `P1405-005`, `P1405-006`, `P1405-008`
  - 告知・通知文面は、利用者や関係者への対外説明に近く、断定ミスや未確認情報の混入が危険なため
- `P1406-003`, `P1406-004`
  - 再開支援は、存在しない決定事項や未完了事項を混ぜると次回作業を誤誘導しやすいため

### 弱い版にした代表理由

- `P1101-*`
  - 前提、制約、課題、依存の整理には再構成が必要だが、存在しない前提や依存を作ってはいけないため
- `P1102-*`
  - 時系列、因果、根本原因候補の整理では一定の分析が必要だが、断定しすぎると誤誘導になるため
- `P1103-003-P1103-006`
  - 主張と根拠の切り分けは推論を含むが、根拠の有無や出典要否を捏造してはいけないため
- `P1005-005`, `P1005-010`, `P1005-011`
  - 影響範囲やリスク整理は推定を伴うが、事実と推測を分離できれば実用性を保てるため
- `P1005-001-P1005-003`, `P1005-006-P1005-009`
  - セキュリティや観測は高リスク領域だが、主目的は整理や設計観点の明確化であり、分析の余地を残したほうが実用的なため
- `P1003-001-P1003-004`
  - 矛盾確認や仕様穴検出は点検用途が主だが、入力にない仕様を埋めたり、矛盾を誤認したりしないよう抑制は必要なため
- `P1004-001-P1004-006`
  - チェックリスト、受け入れ条件、テスト観点は整理と補助が主目的であり、確認漏れ防止の自由度は残しつつ、未確認事項の断定だけ抑えたい帯のため
- `P1205-001-P1205-008`
  - 依頼の明確化や資料向け再構成は再編集が主目的だが、入力にない依頼意図や結論を自然に補ってしまうと誤った共有物を作りやすいため
- `P1301-001-P1301-006`
  - 比較、推奨、コスト整理は判断支援として使われやすく、比較軸や前提、コスト要因を根拠なく足しすぎない抑制が必要なため
- `P1302-001-P1302-006`
  - 優先順位づけは整理が主目的だが、入力にない制約や重要度を当然視すると判断順を誤らせやすいため
- `P1303-001-P1303-002`
  - 問い直しや再定義は再構成を含むが、元の依頼にない論点へ飛びすぎず、前提の置き換えを自覚的に扱う必要があるため
- `P1304-001-P1304-004`
  - 反証や反対意見は仮説的な思考を含むが、存在しない事実や立場を当然のように持ち込むと議論を不必要に歪めるため
- `P1305-001-P1305-004`
  - 評価基準や KPI は後続判断の土台になりやすく、入力にない成功条件や測定前提を当然のものとして置かないようにしたいため
- `P1401-001-P1401-004`
  - 計画化やユースケース整理は推論を含むが、存在しない工程や利用者像を当然のものとして足すと、そのまま実行や設計の誤誘導につながるため
- `P1402-001-P1402-006`
  - スコープや期待値調整は境界整理が主目的だが、入力にない制約や対象外を作ると関係者認識をずらしやすいため
- `P1403-002`
  - レビュー依頼文は共有物として送られやすいが、主目的は状況整理であり、見てほしい点や前提を入力にない形で盛りすぎない抑制があれば十分なため
- `P1403-003`, `P1403-004`
  - 質問生成は創作より整理が主目的であり、現状の不足点から自然に導く範囲に抑えたいため
- `P1404-001-P1404-002`
  - 会議支援は決定事項そのものではないが、議題や宿題を入力にない形で足しすぎると会議運営を誤らせるため
- `P1405-001-P1405-004`
  - 説得や合意形成、ステークホルダー整理は調整支援として有用だが、相手の関心や対立点を根拠なく作ると関係者調整を誤らせるため
- `P1406-001-P1406-002`
  - 運用手順や障害時フローは共有物として使われやすいが、主目的は整理であり、未確認の手順や連絡経路を勝手に補わない抑制があれば実用性を保てるため
- `P1502-001-P1502-002`

### 不要にした代表理由

- 翻訳、平易化、単純リライト
  - 主目的が表現変換であり、防止ルールを強く入れると自然な言い換えを不必要に抑えやすいため
- 発散、代替案、問い直し、優先順位づけ
  - 推論や発想の広がり自体が価値なので、ハルシネーション防止ルールより思考の自由度を優先したため
- 命名候補
  - 複数案を広げて比較する発散性が主価値であり、防止ルールよりネーミング探索の自由度を優先したため
- 憑依系
  - 役割視点の切り替えが主目的であり、防止ルールの文言を重ねるより役割の没入感を保つほうが有用なため
- 倫理・配慮の確認系
  - もともと断定抑制や注意喚起の性質が強く、別ルールの追加効果が比較的小さいため
- 学習支援
  - 事実誤認コストはあるが、出力がそのまま運用物になる度合いは比較的低く、今回の監査でも追加ルールの優先度を上げなかったため
- 翻訳、JSON、資料骨子、可視化準備
  - 出力形式の変換や下準備が主目的であり、追加ルールよりも形式変換の素直さを優先したため

## 新規候補追加時の判定テンプレート

`P` 系列に新しい候補を追加するときは、まず次の順で判定します。

1. その出力は、そのまま運用物や共有物になるか
2. 会話や入力にない事実を補完すると事故になりやすいか
3. 推論や再構成は必要か
4. 主目的は整理か、表現変換か、発散か

この判定に対する目安は次のとおりです。

- `強い版`
  - 報告、通知、再開支援、決定事項抽出のように、そのまま記録や共有に使われやすい
  - 事実誤認や補完ミスのコストが高い
- `弱い版`
  - 前提整理、依存整理、因果整理、根拠整理、図解化のように、再構成や分析は必要
  - ただし、事実と推測の分離は必要
- `不要`
  - 翻訳、単純リライト、平易化、発散、憑依のように、主目的が表現変換や視点切替
  - 防止ルールを足すより、自由度を残すほうが効果的

迷った場合は、次の優先順で判断します。

- まず `強い` を検討する
  - そのまま外部共有や運用判断に使われるなら `強い`
- 次に `弱い` を検討する
  - 事実整理や図解化で、推測混入だけ抑えたいなら `弱い`
- 最後に `不要` を選ぶ
  - 主目的が表現変換や発散で、抑制の利益が小さい場合に限る

追加時に短く記録するなら、次の形式が扱いやすいです。

```markdown
- 対象:
  - `Pxxxx-yyy`
- 判定:
  - 強い / 弱い / 不要
- 理由:
  - そのまま運用物になるか
  - 推論や再構成が必要か
  - 補完ミスのコストは高いか
```

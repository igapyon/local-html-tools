# prompt-definitions-popular 再編案

`P` 系列の番号帯が `P999` に近づいてきたため、単なる継ぎ足しではなく、上位カテゴリと番号帯をあらためて整理するための再編案をまとめます。

この案では、現在の並びをいったん前提にせず、「人が何をしたいかの流れ」に沿って `P` 系列を並べ直します。

## 基本方針

`P` 系列は、次の流れで並ぶのが自然です。

1. まず事故を防ぐ
2. 何が起きているか把握する
3. どう伝えるか整える
4. どう比べて決めるか考える
5. どう進めるか段取る
6. どう残して育てるか整える
7. 必要なら図や読解へ広げる

この流れに沿って、`P` 系列を次の章立てで再編します。

- `P1001`

- `P1004`

- `P1005`
  - 見落としリスク、セキュリティ、観測、インシデントのような事故予防と事故対応に近い守りを後段にまとめられる

| 新番号帯 | 新カテゴリ案 | 役割 | 主な現行カテゴリ |

| `P13xx` | 比較・評価・判断 | 比較、推奨、優先順位、問い直し、反証、評価基準、意思決定記録など、判断のための整理 | `P925-P936` |
| `P14xx` | 計画・会議・実行 | 計画、スコープ、期待値、依頼、質問、会議、通知、運用、再開支援など、前に進めるための運用系 | `P937`, `P939`, `P942`, `P943`, `P945-P954`, `P959` |

## 再編時の原則

- まず `P10xx` を先頭に置き、守備的な確認を入口にする
- 現行の 3 桁番号や枝番へのこだわりは捨て、4 桁番号の章立てへ寄せる
- 似たものは新章を増やさず、既存章へ寄せる
- 各章は `100` 刻みで管理し、内部は原則連番で振る
- `P16xx` と `P17xx` は応用章として後段に置く

## 最初に着手するなら

再編作業を始める場合は、まず次の順で進めるのが安全です。

1. 新しい上位カテゴリ名と番号帯を確定する
2. `prompt-definitions-popular.md` の上位カテゴリを新章立てで書き直す
3. 現行 `P9xx` を新しい `P10xx` 以降へ写像する対応表を確定する
4. `prompt-definitions-popular.ts` のラベル番号と `keywords` を一括更新する
5. `README.md`、`TODO.md`、生成物、テストを追従させる

## 実施手順案

実際に再編する場合は、番号を場当たり的に置換せず、次の順で進めるのが安全です。

1. 再編正本を確定する
   - この文書を正本として、`P10xx-P17xx` の章立てとボタン単位移行表を最終確定する
   - 特に `P902` の置き場と、`P911-001 / P911-002` の分離を確定する

2. 文書側の新体系を先に整える
   - `prompt-definitions-popular.md` を新しい章立てと番号帯で書き直す
   - `README.md` と `TODO.md` に新番号帯の説明を追従する

3. 定義本体を一括更新する
   - `prompt-definitions-popular.ts` の `label` を新番号へ置換する
   - `keywords` に含まれる旧 `Pxxx-yyy` も新番号へ追従する
   - `id` は無理に番号連動へ変えず、必要がなければ現状維持でもよい

4. 旧番号の残存を機械的に確認する
   - `rg "P9[0-9]{2}" docs/prompt` などで、旧番号が残っていないか確認する
   - ただし履歴メモや再編案文書のように、意図的に旧番号を残す場所は除外する

5. 生成物を更新する
   - `npm run build:prompt`
   - `prompt-gen.html` と生成済み `js` を追従させる

6. 最小回帰を確認する
   - `npm test -- docs/prompt/tests/prompt-gen-main.test.js`
   - 必要なら、代表的な `P` 番号で検索ヒット確認も追加する

## 一括置換時の注意点

- 旧番号から新番号への対応が多いため、単純な連番置換ではなく、この文書の移行表を正本にして置換する
- `keywords` に番号文字列が入っているため、ラベルだけでなく検索用キーワードの更新も漏らさない
- `prompt-definitions-popular.md`、`README.md`、`TODO.md`、生成済み `js`、`prompt-gen.html` の整合を必ず取る
- 旧番号が user-facing な共有リンクや説明文に残る可能性があるため、主要な番号は最低限検索確認を行う
- 一度に全部置換する場合でも、文書更新、定義更新、ビルド、テストの順を崩さない

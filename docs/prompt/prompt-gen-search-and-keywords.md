# prompt-gen 検索とキーワード設計

`docs/prompt/prompt-gen.html` の検索ボックス挙動と、`docs/prompt/src/prompt-gen/ts/prompt-definitions.ts` における `keywords` 設計方針をまとめる。

## 対象

- 検索 UI: `docs/prompt/src/prompt-gen/ts/main.ts`
- 候補定義: `docs/prompt/src/prompt-gen/ts/prompt-definitions.ts`

## キーワード設計方針

- まず `label` の語を起点に考える
  - 番号、記号、助詞など検索語として弱い部分は除いて、用途名、対象名、固有名を拾う
- `label` の語は検索対象そのものでもあるため、`keywords` に必ず重複して入れる必要はない
- `keywords` は候補検索を助けるための補助語であり、`label` や `buildBody()` だけでは拾いにくい別名や表記揺れを補完する
- 本文 (`buildBody()`) からは、その候補を探す人が実際に入力しそうな特徴語を補う
  - 用途語
  - 出力形式
  - キャラクター名、規格名、技術名などの固有語
- 用途語や出力形式の語も、実際に検索されそうであれば含める
  - 例: `markdown`, `jsonl`, `persona`
- 日本語と英語の両方を必要に応じて含める
- ひらがなは検索補助として比較的積極的に追加する
- かな読み、ローマ字は必要そうなものだけを追加する
  - 全語を機械的に展開する運用ではない
- 広すぎる一般語をむやみに増やさず、その候補を探す人が実際に入力しそうな語を優先する
- 新しい候補を追加するときは、最低限「label 由来の語」「本文由来の特徴語」「表記揺れ」の3観点で不足がないか確認する

## 検索ボックスの挙動

### 基本挙動

- 検索欄が空欄のときは、全候補を `label` の昇順で表示する
- 検索語は空白区切りで AND 条件として扱う
  - すべての検索語を満たした候補だけが残る
- 検索語入力時は小文字化して比較する

### 照合対象

- 候補検索は次の3系統で行う
  - `label` 由来の語
  - `keywords`
  - `label` と `keywords` から展開した補助語
- 表示順の優先度は次のとおり
  1. `label` 一致群
  2. `keywords` 一致群
  3. 展開語一致群
- 複数群にまたがって一致しても、同じ候補は1回だけ表示する

### `label` 由来の語

- `label` 全体を1語として扱う
- さらに空白で分割した各部分も検索対象にする
- たとえば `801: 会話相手: みくく` なら、`label` 全体に加えて、空白で区切られた部分も照合対象になる
- `label` そのものが検索対象であるため、`keywords` に同じ語を必ず重複登録する必要はない

### `keywords`

- `keywords` に登録された各語を検索対象にする
- 各キーワードはそのままの形に加えて、空白で分割した語も検索対象にする
- `keywords` は `label` だけでは拾いにくい別名、特徴語、表記揺れを補う用途で使う

### 展開語

- `label` と `keywords` の各語から、補助的な展開語を生成する
- 展開では次を扱う
  - ひらがな化
  - カタカナ化
  - かなをローマ字化した語
- 展開語は元の `label` / `keywords` 本体とは別の第3優先群として扱う
- そのため、まず `label` や `keywords` の直接一致が優先され、展開語一致はその後ろに並ぶ

### 並び順と優先順

- 検索結果の並び順は、群ごとに次のルールで決まる
  - `label` 一致群は `label` 昇順
  - `keywords` 一致群と展開語一致群は、検索語との一致の強さで並べる
- 一致の強さは、検索語がどれだけ短いトークンに強く一致しているかで計算する
  - より短く、より直接的に一致する候補が上に来る
- 同点の場合は `label` 昇順で安定化する

### プライマリ候補の決まり方

- 検索結果が複数あっても、次の条件を満たすと1件を自動選択する
  1. `label` 一致群が1件だけのときは、その候補を選ぶ
  2. `label` 一致群が0件で、`keywords` 一致群が1件だけのときは、その候補を選ぶ
  3. 上記が成立せず、展開語一致群が1件だけのときのときは、その候補を選ぶ
- この自動選択された候補が、画面上ではプライマリ候補として `is-active` 状態になる
- 自動選択が成立しない場合は、候補は表示されるが自動では確定しない

### 検索変更時の状態リセット

- 検索文字列が前回から変わると、現在選択中の候補をクリアする
- あわせて次もリセットする
  - commit ID 入力欄の値
  - 生成結果
  - 出力欄表示状態
- そのうえで、新しい検索結果に対して再びプライマリ候補判定を行う

### 候補選択時の UI 挙動

- 候補ボタンをクリックすると、その候補を選択状態にする
- 選択時は出力欄を表示する
- 検索欄が空欄の状態で候補ボタンをクリックした場合は、候補ラベルの系列番号から親番号だけを取り出して検索欄へ入れる
  - 例: `A321` をクリックした場合は `321`
  - 例: `P1004-003` をクリックした場合は `1004`
- 検索欄にすでに文字が入っている場合は、この自動補完は行わない
- `requiresCommitId` が `true` の候補では commit ID 入力欄を表示する
  - この場合は commit ID 入力欄へフォーカスを移す
- `requiresCommitId` が `false` の候補では commit ID 入力欄を隠す

### 出力テキストの生成

- 出力は `buildBody(commitId)` の結果をもとに生成する
- `requiresCommitId` が必要な候補では、commit ID が空の間は本文が空のままになることがある
- `includeLabelPrefix` が ON のときは、先頭に `[label] ` を付与する
- `includeLabelPrefix` の切替や commit ID の変更は、その場で出力へ反映する

### コピーの挙動

- 候補を手動クリックしたとき、`requiresCommitId` が `false` の候補は自動でクリップボードへコピーする
- コピー対象は、その時点で出力欄に表示されている全文である
- `requiresCommitId` が `true` の候補は、commit ID 未入力の可能性があるため自動コピーしない
- コピー成功時は `コピーしました`、失敗時は `コピーに失敗しました` の toast を表示する
- Clipboard API が使えない環境では、`textarea` を一時生成して `execCommand("copy")` にフォールバックする

## A501 の特記事項

- `A501: GitHub PR 文面の作成` を選択したときだけ、出力オプション行に `Git pseudo-squash で整理` の外部リンクを表示する
- リンク先は `https://igapyon.github.io/local-html-tools/git/git-pseudo-squash.html` 固定とする
- この導線は他ページからの連携前提でも使うため、A501 向けのリンク先パスは不用意に変更しない
